# 質問（Yuki・Fable へ）

## Q1. 【解決 11/3】関所は `kurokofude mask` と生成コマンドを通すか（Yuki／Fable）

**回答（Fable）**：どちらの案でもなく、許可リスト方式。`kurokofude mask`、`kurokofude batch`、`python tools/make_dummy/make.py` だけ通し、正解データは `data/truth/` へ移して氏名の文字列を持たない。design.md §4.1・§6 に反映済み。以下は当時の記録。

**矛盾**：design.md §4.1 は「コマンドに保護ディレクトリを含めば止める」。CLAUDE.md は Claude が `kurokofude mask data/raw/xxx.tif` や `python tools/make_dummy/make.py --out data/raw` を実行する前提。実際に実行するとフックで止まる（11/3 確認）。例外を作ると関所の抜け道になるので、自分では決めず、フックはそのまま厳しくしてある。

**止まっている作業**：`data/raw/` への5枚の生成と、そこに対する `mask` / `eval`。正解JSONも同じ場所にあるので `eval` も止まる。

**選択肢**：
- A（当面のおすすめ）：Claude には例外なし。Yuki がプロンプトで `!` を付けて実行する（`!` の実行はフックを通らない）。11/6 に `mask_drawing` ができれば、Claude はそちらを使う。デモの筋書き（§4.3）とも一致
- B：`kurokofude mask|batch|eval` と `make.py` だけ、完全一致でフックの例外にする。楽だが、`;` などのつなぎ方を含めて例外の検査が必要になる

Yuki 用のコマンド（Aの場合）：
```
! python tools/make_dummy/make.py --source data/source --out data/raw --count 5
! kurokofude mask data/raw/dummy_001.tif
! kurokofude eval --truth data/raw/dummy_001.truth.json --result data/masked/dummy_001.chiban.json
```

## Q2. 【解決 11/3】塗る条件を決めてほしい（Fable）

**回答**：design.md §11.1〜11.5 に反映済み。以下は当時の記録。

氏名カバー率 61%（目標 99%）。5枚の OCR キャッシュで条件だけ変えて比べた。**設定とコードは変えていない**（下の数字は比較実験で、精度の記録には入れていない）。

| 条件 | 氏名カバー率 | 塗りすぎ率 | 地番生存率 |
|---|---|---|---|
| 現行（最も近い1つ、下へ +2px で切る） | 61.24 | 30.57 | 99.41 |
| 余白 0px | 67.36 | 29.86 | 98.75 |
| 上へ 4px（地番側に食い込む） | 71.03 | 36.24 | 64.37 |
| 切らない | 71.21 | 43.76 | 22.74 |
| 全候補を塗る、下へ +2px | 65.81 | 35.35 | 92.76 |
| 全候補を塗る、切らない | 75.99 | 46.01 | 20.29 |

原因は3つで、どれも §2.3 のままでは解けない：

1. **地番の取りこぼしが一番大きい（検出率 平均 72.68%）。** 切らず全候補を塗っても 76% で頭打ちになる。筆界線が文字にかかると `273/9`、`273.19`、`3-` と `10` への分断などになる。→ 正規化に `/` `.` → `-` を足してよいか。分断された地番はどう扱うか
2. **切る線が氏名の上端を削る。** 地番の OCR 枠は文字より下に余白があり、その下辺で切ると氏名まで切れる。一方、OCR の氏名枠は地番の文字に重なるので、切らないと地番を塗る（生存率 23%）。→ `cut_margin_px` の向きは「下へ」でよいか（設計書の「＋余白」をそう解釈した）。枠の下辺ではなく、画素を見て文字の実際の下端を求めてよいか
3. **氏名が2つの枠に割れる。** 401 件中 98 件が OCR の枠2つ以上にまたがる（姓と名の間の空白や、筆界線で切れる）。「最も近い1つ」だと**片方の名前がそのまま残る**。→ 同じ行にある枠は全部塗る、としてよいか。全候補を塗ると隣の地番の範囲まで取り、生存率が 92.76 まで落ちるので単純には足せない

**私のおすすめ**：3 → 2 → 1 の順に効かせるより、まず 1（検出率）と 2（切る線）。残る氏名の漏れは個人情報そのものなので、3 も目標 99% には外せない。

**確認したいダミー側の前提**：地番と氏名の間隔を 0.5mm（約4px）で描いている。実際の図面の間隔が分かれば `name_gap_mm` を合わせたい（Yuki）。また、斜めの氏名のカバー率は 48.5%、水平は 66.3%。

## Q3. 【解決 11/3】長辺で角度を決めると1桁の地番が倒れる（Fable）

**回答**：design.md §11.6 に反映済み。以下は当時の記録。

§2.3 は「angle は四角形の長辺方向」。`5` のような1桁の地番は枠が縦長なので角度が 90° 前後になり、氏名との角度差で必ず弾かれる見込み。今回の5枚には1桁の地番がなく未確認（コードは設計どおり長辺）。→ 「水平から ±45° に入る辺を読み方向とする」に変えてよいか。45° を超えて倒れた注記は実務にあるか（Yuki）。

## Q4. 【解決 11/3】関所に残っている穴（Yuki／Fable）

**回答**：design.md §11.8 に反映済み。以下は当時の記録。

次はフックを通る（判定だけ確認、実行はしていない）。§4.1 の単純なルールの範囲外なので、どこまで塞ぐか決めてほしい。

- 親フォルダからの再帰：`grep -r x data`、`ls data`、`find data`
- 文字列を組み立てるスクリプト：`python -c` でパスを連結する、パスをスクリプトの中に書く
- 許可リストの中身の書き換え：`tools/make_dummy/make.py` や `src/kurokofude/`、`configs/default.yaml` は Claude が編集できるので、許可されたコマンドの中身を変えれば読めてしまう（11/3 追加）

コマンド文字列の検査では後者を完全には塞げない。デモ用の関所としては十分でも、「安全です」とまでは言えない。→ README に「誤操作を防ぐもので、悪意のある回避は防がない」と明記するのがおすすめ。OS の権限で守るなら別途設計が必要。

## Q5. 【解決 11/3】除外領域が広すぎて、氏名が塗られず残る（Fable／Yuki）

**回答**：design.md §12.1 に反映済み。以下は当時の記録。

既定の `exclude_regions: [0.6, 0.8, 1.0, 1.0]` は画像の8%を占める。ダミーの表題欄は実際には画像の約0.5%（360×110px）なので、その周りの筆の氏名が塗られない。氏名が0%しか塗られなかった41件のうち **40件がこの領域の中**にあった。実物の図面でも、この範囲の氏名は確認画面で気づかなければ残る。

設定だけ変えて測った結果（`default.yaml` は変えていない。精度の記録にも入れていない）：

| 除外領域 | 氏名カバー率 | 塗りすぎ率 | 地番生存率 | 地番検出率 |
|---|---|---|---|---|
| 現行 `[0.6, 0.8, 1.0, 1.0]` | 88.94 | 26.27 | 95.79 | 89.61 |
| 表題欄の大きさ `[0.88, 0.94, 1.0, 1.0]` | 99.12 | 26.49 | 94.71 | 98.49 |

→ 既定値を狭めてよいか。ただし表題欄の位置と大きさは図面ごとに違うので、値だけの問題ではない。候補：
- A：既定を狭くし、図面の種類ごとに設定で合わせる。`sample_small` は表題欄が画像の約5%なので別の設定が要る
- B（おすすめ）：除外領域の中も塗らないのではなく、**地番の下の枠は領域の中でも塗る**、または領域内の枠を unpaired として②で人に見せる。塗り漏れの側に倒れる既定をなくせる
- 実物の表題欄の大きさと位置の傾向を教えてほしい（Yuki）

## Q6. 【解決 11/3】地番の生存率 100% に届かない。unpaired が地番を塗る（Fable）

**回答**：design.md §12.2 に反映済み。ただし副作用あり（Q8）。以下は当時の記録。

生存率 95.79%（目標 100%）。塗られた地番を調べると13件で（面積での簡易集計）：
- 9件：地番とは別の unpaired の枠が地番に重なっている（地番の切り離しは auto にしか効かない）
- 3件：地番を読めず、氏名と一体の枠として (c) に入った
- 1件：別の地番の auto の枠が重なっている

→ 「**(a) の地番の枠に重なる部分は、どの塗りからも切り取る**」を足してよいか。9件と1件は救えるはず。OCR の地番の枠は下に余白があるので、そのまま切り取ると氏名の上端を残す恐れがあり、§11.3 と同じインクの谷で切るのがおすすめ。残る3件は①では判別できず、②で人が直す範囲か。

## Q7. 【解決 11/3】余白3pxのままでは塗りすぎ率 15% に届かない（Fable）

**回答**：design.md §12.3 に反映済み。以下は当時の記録。

塗りすぎ率 26.27%（目標 15% 以下）の内訳は auto が 25.6%、unpaired が 40.8%。auto はインクまで詰められていて、**残りはほぼ §11.3 の余白 3px の分**。氏名の高さが約20pxなので、上下左右に3px足すと計算上 約27%になる。余白 1px なら計算上 約11%。ただし余白を減らすと、かすれた字や正解の枠の誤差で塗り漏れが増える恐れがある（未測定）。

→ `tighten_padding_px` を文字の高さに比例させるか、塗りすぎ率の目標を見直すか。塗り漏れより塗りすぎのほうが安全という §11 の方針からは、目標の見直しがおすすめ。

## Q8. 【止まっている】地番の枠を引くと、氏名の上端が塗られず残る（Fable）

§12.2 を指定どおり入れると、地番生存率は 94.14% → 99.22% に上がったが、氏名カバー率が 98.97% → 92.43% に下がった。OCR の地番枠は文字より下に余白があり、そこに重なる氏名の上端まで塗りから引かれるため。

地番の枠の下側を §11.3 と同じくインクの谷で詰めてから引くと、地番を守ったままカバー率が戻る。5枚で比較した結果（比較実験。設定とコードは変えていない。精度の記録にも入れていない。保護ディレクトリの外に同じシードで生成した図面で測定）：

| 引く枠 | 氏名カバー率 | 塗りすぎ率 | 従来の定義 | 地番生存率 |
|---|---|---|---|---|
| 現行：OCR の枠をそのまま | 92.43 | 10.51 | 27.41 | 99.22 |
| 案：枠の下半分でインク最小の行まで詰める | 98.83 | 9.69 | 28.65 | 99.22 |

→ 案を採用してよいか（おすすめ）。カバー率の目標 99% にも、あと一歩になる。

## Q9. 氏名と地番が1つの枠になると、(b) で氏名の一部が残る（Fable）

数字の割合が 0.5 以上で許可外の文字を含む枠（`□□□273-10` のように、OCR が地番と氏名の一部を1つにしたもの）が、5枚で3件あった。(b) は残すので、この枠に入った氏名の文字は塗られず、さらに §12.2 で保護される。「数字なので個人情報ではない」という §11.1 の前提が、この3件では成り立たない。

→ `□` を含む (b) は、残すのではなく塗る側（status を分けて②で人が見る）に倒してよいか。塗ると地番が消えることがあるが、塗り漏れより安全という方針には沿う（おすすめ）。残る地番生存率の不足（5枚で3件）の扱いと合わせて判断してほしい。
