# 黒子筆（Kurokofude）— AIに図面を渡す前の関所

スキャンした測量図面から、地権者の氏名だけを手元のPCで塗りつぶし、安心してAIに渡せるようにする道具です。名前の「黒子」は、黒く塗ることと、舞台の陰で支える黒子の掛け言葉。「筆」は塗る筆と、土地の単位「一筆」の掛け言葉です。

## インパクト

私は、自治体の河川区域をデジタル化し、GISで管理・共有しやすくする仕事をしています。担当者が減っても管理を続けられるようにするためのDXです。河川管理の境界確定と、道路台帳の区域線図作成では、スキャンした台帳図面の位置合わせが要ります。その図面には、地番の下に地権者の氏名が書かれています。

位置合わせをAIに任せたくても、個人情報の入った画像をそのまま渡すわけにはいきません。今はペイントで1枚ずつ氏名を塗っています。シンプルな図面でも1枚2分、台帳単位では膨大な量です。ペイントは水平な四角しか描けないので、斜めの文字を塗ると周りの線まで消え、位置合わせの精度にも響きます。

黒子筆は、氏名は消して、地番は残します。地番が位置合わせの鍵だからです。地番そのものは法務局が公開しているデータにある情報で、個人情報には当たらないと考えています。ただし、台帳図面をAIに渡すことの扱いは現時点では発注者ごとに考えが異なるので、使うときは発注者の承諾を得ることを前提にしています。国土交通省はAIの利用を推進する方向で、労働力の減少に対応するために国や自治体のDXも加速します。このような関所の必要性は、近い将来さらに増すと考えています。ハッカソンの後は、発注者の了解のもとで自社の標準手順にし、12月の同業者の会で紹介します。個人情報の壁でAIを使えずにいる小さな測量会社や自治体にも届けたいと思っています。

## デモ

冒頭で図面1枚を使い、「地番とは何か」「なぜその下に名前があるのか」を見せてから、3つの場面を流します。①塗る前の図面をClaudeに開かせようとすると、関所に止められる。②「地番を教えて」と頼むと、スキルが黒子筆を呼び、塗った図面と地番の一覧だけが返り、人が確認画面で確定する。③わざと約43mずらした図面を、Claudeが地番だけで公図データと照合し、紙の上で3mmほどのずれまで戻す。冒頭は本物の筆で氏名を塗る実写から入り、ペイントでの苦労を見せます。

## Claudeの活用

「Claudeが生データを見ずに仕事をする」という形を、Claude Codeの機能の組み合わせで作りました。フックとdeny設定が、塗る前の図面への直接アクセスを止めます（止めたときは、どの規則で止めたかを伝えます）。MCPサーバーのツールは3つだけで、どれも生画像・塗る前のパス・氏名の文字列を返しません。確認画面は人の道具で、ClaudeはURLすら受け取りません。スキルは「塗る→人の確定を待つ→照合」の手順を持ち、サブエージェントが公図との照合を担います。検証では、Claudeは最初からスキル経由で黒子筆を使い、塗る前の図面を一度も読もうとしませんでした。

開発もClaude Codeが中心です。私が方針を決め、Fableが設計し、Opusが実装する役割分担で、CLAUDE.mdに規約を書きました。Opusは判断に迷うとquestions.mdに書いて止まり、Fableと私が答えます。関所は開発の初日から効いていて、実装担当のOpus自身も何度も止められました。その誤検知の記録から、止めた理由を伝える機能が生まれています。コードはすべて期間中に新しく書き、事前実験からは知見だけを引き継ぎました。

## 深さと実行力

設計の芯は3つです。氏名は読まずに見つける（文字列を保存しない）。画素の位置を動かさない（ワールドファイルがそのまま使える）。迷ったら塗って、人が外す。

精度はダミー図面5枚で測り、測るたびにaccuracy_logに1行ずつ記録しました。氏名カバー率は初日の61%から99.7%になりましたが、この伸びには図面を実物に寄せた効果や指標の定義の変更も含まれ、記録でどれが変わったかを区別しています。現場の目視で見つかった塗り残しは、原因（氏名と隣の地番が1つの枠に読まれていた）を突き止めて直しました。地番生存率は99.68%で目標の100%に届いていません。だから黒子筆は塗り漏れゼロを保証せず、人の確認を手順に含めます。

会社のPCはWindowsなので、インストールからOCR、塗り、採点までをGitHub ActionsのWindowsランナーで毎回確かめています。設定は図面に合わせて変えられ、表題欄の位置や地番の桁数、河川図面向けのプリセットを用意しました。

図面は法務省 登記所備付地図データ（G空間情報センター）を加工して作成し、氏名はすべて架空です。
